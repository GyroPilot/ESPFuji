# ESPFuji through a Lisa driver: status, 11 November 2026

A progress note on the driver idea discussed on LisaList2 (topic 897), published because the design was asked for
before the code. Short version: the Lisa side is built and runs in LisaEm, the drive side is written and passes
its PC tests, and the two have not yet met. Nothing has run on a real Lisa, nothing is released, nothing has been
flashed to any ESProFile.

## What the pieces are

- A loadable Lisa Office System driver, SYSTEM.CD_ESPFDEMO, written in Workshop 3.0 Pascal and assembler from
  Apple's five driver support files and loaded at run time the lisa-share way (CDMAKE at the start, CDKILL at
  the end). It installs at the console position, channel 3, because the OS refuses to start a driver in an
  empty expansion slot (error 609), and it owns no hardware: it reaches the drive THROUGH Apple's ProFile driver,
  the way the file system's own DISKIO does (the "Option A" from my 1 November reply).
- A plain Office System tool, "ESPFuji Driver", which attaches the driver when opened, shows the drive's status
  block as text and hex, and takes the driver out when put away. If the boot volume has no driver file, the tool
  copies its own from the floppy, so the whole test is: insert the floppy, open the tool.
- The drive side: the channel, written as one small hardware-free file in a private copy of the ESPFuji firmware.
  It compiles for the ESP32 and has not run on one yet. About 2.3 KB of flash and 5 KB of heap.

## What has been shown, all in lisaem

- Reads through Apple's driver work while that driver is serving the boot volume: block 0 came back as block 0,
  a request for the spare table came back as the spare table, and a read of the emulator status block went out
  on the cable exactly as the ESProFile expects it. The disk driver's own state was unchanged afterwards.
- Writes work the same way; shown with a test-only build on a free block of a scratch disk, read back and put
  back, block and tag byte-identical afterwards. The ordinary build can write ONE block only, the channel block,
  and only after a probe read of that drive has found a channel there. Against a plain image the probe says "no
  channel" and every write is refused, which is what a stock ESProFile gets today.
- Sessions: a tool asks the driver for a client id (1 to 8) and gives it back at the end; the driver sends the
  session's opening cancel itself before the first request and the closing cancel when the session is returned,
  never at CDKILL time (the shut-down call runs with interrupts off and must not wait for I/O).
- The tool has the channel on its keys: C probes the channel block and shows the drive's identification line
  (or the stray block a stock drive answers with, as hex); H sends HELLO through the channel and reads until
  the reply is ready. Against LisaEm's plain image the probe says no channel; against an imitation of the
  channel drive on the PC the whole exchange runs. Each half has been tested against an imitation of the other.
- Writing that PC imitation found a fault the LisaEm run could not show: the driver built its deferred cancel in
  its one block buffer and blanked the request's payload behind it, so a session's first request would have
  reached the drive empty. Fixed and re-checked both ways. Driver REV F, tool REV H.

## The channel, in brief (the full specification is ESPFUJI_CHANNEL_SPEC.md beside this file)

- One reserved block, $FFFEF8. The host writes a 512-byte request and reads the same block back for the reply.
  Nothing is stored in the image; the tag carries nothing.
- The block is the ESPFuji mailbox page, protocol version 3: signature, version, sequence number, kind (request,
  poll, cancel; reply), payload length, a client id and a status word, then up to 492 bytes of payload. The
  requests are the ones the file mailbox already has (HELLO, WIFI, CLOCK, OPEN, READ, CLOSE), so only the
  transport changes.
- A read answers PENDING, READY with the payload, REFUSED with a reason, or IDLE with an identification line.
  Reads are idempotent: the reply stays until the client's next request or a cancel, so a retried read cannot
  swallow it.
- Requests are keyed by client and sequence number, because Apple's driver re-sends a failed command up to four
  more times; repeats are ignored. A client opens with a cancel, so a program restarted with the same id is not
  handed the previous session's answer.
- The drive answers every command at bus speed and does the network work on its other core; the host polls.
  Apple's driver's timeout (about 10 s) stalls the whole disk queue, so the drive never holds BSY.
- A few slots per drive (four on a plain ESP32), one per client id. The file mailbox stays for programs without
  a driver, and the Selector's blocks are untouched.

## Four things learned on the way, for anyone else talking to a drive from the lisa os

- Apple's ProFile driver remaps the low four bits of every block number for the interleave (5n mod 16), for every
  ProFile-type drive including the ESProFile; MacWorks uses the inverse order. Both leave 0, 4, 8 and C alone,
  which is why the channel is $FFFEF8 and not $FFFEFB: the same number from the OS, from MacWorks and from a
  bare-metal program.
- Retry count and sparing threshold are fixed per drive by the driver (10 and 3), so a protocol cannot use them,
  and a multi-block request is remapped block by block, so requests must be single blocks.
- The tag of a reply must be all zeros. Bit 7 of tag byte 6 switches on the OS's checksum check, and top bits
  in tag byte 2 come back as warnings -626 and -625.
- Never WRITE a reserved block to a drive that has not identified itself. The stock firmware's range check
  compares the block number with the image size in bytes, so on an image over about 16.7 MB an unknown high block
  passes and the write lands somewhere real. A read is harmless, so the channel is probed by a read.

## Not done, not known

- A real Lisa and a real ESProFile: timing, the error path (LisaEm never refuses a block), the real status block.
- A ProFile on a parallel card. The driver finds those through the configinfo table, reasoned from the source
  and not yet seen.
- Whether MacWorks's ProFile driver passes a block number like $FFFEF8 through at all. If not, the XL side would
  talk to the 6522 directly, as lisa_io does.
- The poll-before-read rule for a second client is in the design and not in the driver yet.
